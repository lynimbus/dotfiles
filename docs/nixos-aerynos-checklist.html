A · 启动可靠性 对应 AerynOS 的 self-healing / 原子回滚

A1
自动引导评估：起不来就自动跳回上一代
system/boot.nix 风险 低 收益 高 纯增量
▶

已实施。system/boot.nix 开启 boot counting，tries = 3，configurationLimit 由 3 提到 5。

验证方式是从构建产物里读生成的 builder，不是看配置文件写了什么：

grep 'BOOT_COUNTING\|CONFIGURATION_LIMIT' $S/boot/bin/systemd-boot
BOOT_COUNTING_TRIES = "3"
BOOT_COUNTING = "True" == "True"      # 真的开了
CONFIGURATION_LIMIT = int("5")        # 真的改了

为什么 configurationLimit 必须一起提到 5：实测 /boot 是 2.0G，已用 179M，每个 initrd 约 72M。菜单只留 3 个世代时，若最新 3 个都被判 bad 就没有可回退的世代。安全值是 tries + 2 = 5，约 430M，仍在余量内。

要等下次写 ESP 才生效。当前启动项的 LoaderBootCountPath EFI 变量还不存在，所以 systemd-bless-boot.service 的 ConditionResult 仍是 no。这是预期行为，不是配置没生效。
回退：把 bootCounting.enable 改回 false 重建。已存在的 +N 后缀由 builder 的 GC 清掉，不用手动动 ESP。
A2
收紧「启动成功」的定义：图形会话真起来才算 good
system/boot-complete.nix（新建） 风险 中 收益 高 依赖 A1
▶

已实施，但我改掉了原方案。

原方案在这台机器上会每次开机都失败。原计划用「Wayland socket 存在」当判据。实测 loginctl show-session 1 是 Service=login TTY=tty1 Type=wayland，而 Linger=no、没有 display-manager.service、getty@tty1 才是登录入口。开机时没人登录就没有 Wayland socket，判据会一次都过不了，boot counting 会在三次后把这个世代永久跳过。

改成等两件开机时本来就该存在的东西：

  • /dev/dri/card* 存在 —— 显卡驱动起来了
  • getty@tty1.service 是 active —— 登录提示起来了

60 秒内等到就放行，超时就 exit 1，boot-complete.target 不可达，这一代不被 bless，计数递减。

# system/boot-complete.nix（新建，已 import 进 system/init.nix）
for _ in $(seq 60); do
  if ls /dev/dri/card* > /dev/null 2>&1 \
    && [ "$(systemctl is-active getty@tty1.service)" = active ]
  then exit 0; fi
  sleep 1
done
exit 1

unit 的三个关键设置（都已从产物里确认）：

requiredBy = [ "boot-complete.target" ];   # 生成 .requires 软链
before     = [ "boot-complete.target" ];
unitConfig.DefaultDependencies = false;   # 否则被排到 multi-user 之后，绕开判据
踩到两个坑，都已修好：
  • 第一版用 compgen -G 检查设备。实测 pkgs.bash 编译时不带 programmable completion，compgen: command not found，脚本 60 秒后必然失败 —— 而失败方向是「永远判 bad」，比不装还糟。改成 ls。
  • Nix 字符串里 ${#cards[@]} 会和插值语法冲突，不能这么写。

验证：在健康系统上跑它，退出码 0 且 stderr 为空（都实测通过）。

A3
把「有 failed unit」也算作启动失败
system/boot-complete.nix 风险 高 收益 低 我建议跳过
▶

systemd 自带一个示例 unit：systemd-boot-check-no-failures.service，逻辑就是「有 failed unit 就不让 boot-complete 达成」。它是 upstream 自带但默认不启用的。

systemd.additionalUpstreamSystemUnits = [
  "systemd-boot-check-no-failures.service"
];
systemd.targets.boot-complete.wants = [
  "systemd-boot-check-no-failures.service"
];

两个 option 我都实测过能正常求值、无 assertion 失败。

我标注「建议跳过」的理由，请自己权衡：
  • 这是「任一 failed unit 即回滚」的极端策略。笔记本上偶发失败的单元太多：蓝牙固件没加载、NTFS 挂载、tlp、zed 之类，都会误伤。
  • 你的 system/hardware.nix 挂了两个 ntfs3 分区（/mnt/windows 有 nofail + automount，/mnt/data 没有 nofail）—— 后者一旦某次启动时 NTFS dirty 就会 failed，白白消耗一次 try。
  • upstream 自己的 man page 就写着："this service is probably not suitable for deployment in most scenarios … primarily useful only as example"。
结论：A2 已经覆盖了真正关心的「桌面起不来」，A3 只是噪声放大器。除非你想要「任何异常都不算成功」的洁癖语义。
A4
「整次更新推迟到一次用户态重启」的工作流（soft-reboot）
justfile 风险 低 收益 中 不改系统，只加命令
▶

这是对 AerynOS「内核级瞬时原子切换」在 NixOS 上能给出的最接近的工程近似 —— 换用法，不换实现。

实测前提：你机器上 soft-reboot.target 与 systemd-soft-reboot.service 已经是 linked 状态（nixpkgs PR #514100 已合入），可以直接用；nixos-rebuild 已经是 nixos-rebuild-ng。

先说一个关键坑：nixpkgs 没有实现 /run/nextroot 的准备（我 grep 过 nixos/ 全树，零命中；对应的 PR #309911 仍是 draft）。所以裸跑 nixos-rebuild boot + systemctl soft-reboot 不会切到新世代，只是把用户态重启回同一个世代。必须自己把 /run/nextroot 指过去。
soft-reboot:
    #!/usr/bin/env bash
    set -euo pipefail
    nh os boot .
    # soft-reboot 会 chroot 到 /run/nextroot —— 必须先指向新世代
    sudo rm -rf /run/nextroot
    sudo ln -sfn "$(readlink -f /nix/var/nix/profiles/system)" /run/nextroot
    sudo systemctl soft-reboot

能省多少：你实测 systemd-analyze 是 firmware 7.973s + loader 5.556s + kernel 2.537s + initrd 3.904s ≈ 20s，全部跳过，只剩 userspace 6.281s。

语义差异必须清楚：你的会话是 tty1 → login → fish → mango（实测 login 是 PID 1 的子进程）。soft-reboot 会 SIGTERM 然后 SIGKILL 所有用户态进程，所以所有终端、GUI、编辑器都会被杀。它等价于「注销并重新登录」，而不是 AerynOS 那种「进程不感知地换根」。真正不感知的换根 NixOS 做不到。

B2
envfs：把 /bin 与 /usr/bin 变成动态 FHS 视图
system/envfs.nix（新建） 风险 中 收益 高 改动 /bin 挂载
▶

已实施。新建 system/envfs.nix，一行开启：

services.envfs.enable = true;

做了什么：把 /usr/bin 挂成 FUSE 视图，内容是「当前进程 PATH 里的所有可执行文件」的符号链接；/bin 再 bind 到 /usr/bin。于是 #!/usr/bin/python3、#!/bin/bash 这类写死路径的脚本直接能跑，不用 patchShebangs。

验证（从构建产物读，不看配置文件）：

  • $S/etc/fstab 里有两条：none /usr/bin envfs bind-mount=/bin,...,nofail 和 /usr/bin /bin none bind,nofail
  • fallback-path 目录里有 env → coreutils/bin/env 和 sh → bash-interactive/bin/sh
  • usrbinenv / binsh 激活脚本命中数 0（模块强制清空）
  • initrd 的 50-envfs tmpfiles 设置确实生成了 /sysroot/usr/bin 与 /sysroot/bin 两个目录
这是清单里最接近「系统底层布局」改动的一项。模块注释明确写了那段 initrd tmpfiles 是在绕开 systemd 的 Refusing to run in unsupported environment where /usr/ is not populated —— 没有那两个目录，开机时 systemd 会直接拒绝启动。挂载全部带 nofail，FUSE 起不来会静默降级，不会卡死。
回退：删掉 system/envfs.nix 那一行并去掉 import 即可，没有任何持久化状态被改动。

C · /etc 归用户 对应 AerynOS 的 stateless / 无三方合并冲突

C1
/etc 改为 overlayfs + 可写 upperdir
system/etc-overlay.nix（新建） 风险 中 收益 高 标记 experimental
▶

已实施。新建 system/etc-overlay.nix：

system.etc.overlay = {
  enable = true;
  mutable = true;   # 默认就是 true，写出来是为了让意图显式
};

做了什么：Nix 生成的 /etc 变成 overlay 的只读下层，你的手改落到 /.rw-etc/upper。升级只重写下层，改动不被覆盖也不产生冲突；删掉 upper 里那个文件就回到生成版本。

验证（从 activate 脚本读）：

  • 出现 mkdir --parents /.rw-etc/upper /.rw-etc/work
  • 两次 mount --type overlay，带 lowerdir=...etc-lowerdir、upperdir=/.rw-etc/upper、redirect_dir=on、metacopy=on
  • 调用 nixos-init/bin/clear-etc-opaque 清理上层残留的 opaque 标记（否则改过的目录会整片遮住下层）
  • /etc/static 命中数 0 —— 旧的符号链接森林确实没有了
  • 1847 条 assertion 全过；initrd 自动带上 erofs、overlay、loop
nixpkgs 把它标为 experimental，原文："Only enable this option if you're confident that you can recover your system if it breaks." 万一 /etc 挂不上，需要能进 initrd 或救援 shell。
一个需要心里有数的语义变化：你的 system/network.nix 里 /etc/resolv.conf 指向 /run/NetworkManager/resolv.conf。overlay 之后这条软链在下层，行为正常；但如果你以后手改 /etc/resolv.conf，那份改动会进上层并永久压住 NetworkManager 的写入。这正是 overlay 的语义，只是要知道。
C2
impermanence：tmpfs root + 白名单持久化
flake.nix（新增 input）+ system/ 风险 高 收益 低 改动巨大
▶

AerynOS 的 stateless 是「包不能写 /etc 和 /var」；NixOS 上最激进的对应物是 nix-community/impermanence 或 anna328p/intransience（后者明确声明兼容 system.etc.overlay，用 systemd-tmpfiles 而非自定义脚本）。

做法：root 挂 tmpfs，每次开机从 store 重新铺开；只有白名单里的路径绑到真实磁盘。

我标"风险 高 / 收益 低"，理由很实在：
  • 它要动 fileSystems."/"，也就是 system/hardware-configuration.nix 里那条 ext4 root。改坏了是开不了机，且不是 boot counting 能救的那种（root 挂不上属于 initrd 阶段失败）。
  • 你机器上已经积累了大量 /var 状态：/var/lib/nixos/networkmanager/system-connections、/var/lib/nixos/user-password-hash（你的 users.nix 依赖它）、gnome-keyring、tuned、docker 之类。白名单要一条条补，漏一个就是数据丢失。
  • 你的 / 是 196G 用了 119G（68G 余量），没有磁盘空间压力，而 tmpfs root 要吃掉一部分 RAM（你 22G 内存，已用 8.6G）。收益不明确。
  • 和 AerynOS 的差距：AerynOS 的 stateless 是「进程写 /usr 会被下次更新回滚」，这是打包约束，不是「开机清空」。impermanence 是另一种东西（安全性取向），语义并不等价。
除非你有明确的安全诉求（防取证、防持久化攻击），否则我建议这一项留在清单外。

D · 性能与缓存 对应 AerynOS 的全发行版 x86-64-v3 / LTO / 文件级 CAS

D1
内核换成 CachyOS LTO + znver4 变体
flake.nix（新增 input）+ system/boot.nix 风险 中 收益 高 有现成缓存
▶

已实施。内核换成 CachyOS 的 linux-cachyos-latest-lto-zen4（7.3.1），Clang + ThinLTO + znver4。

为什么是 release 分支而不是默认分支：实测两条分支代价差几小时。

release 分支  7.3.1   derivations-to-build=0     ← 全在二进制缓存
master 分支   7.3.4   derivations-to-build=18    ← 本地编 LTO 内核，1-3h

你选了 release：内核比原来的 7.3.4 低三个补丁版本，但带 CachyOS 补丁集 + LTO + znver4 优化，仍然是「更优化的内核」。要版本对齐随时可以换分支重编。

# system/boot.nix
kernelPackages =
  inputs.nix-cachyos-kernel.legacyPackages.${pkgs.stdenv.hostPlatform.system}
    ."linuxPackages-cachyos-latest-lto-zen4".extend (...)
踩到一个真 bug，已修：nixos-hardware 的 zenpower 模块编译不过，报
error: unknown warning option '-Wimplicit-fallthrough=3'
根因是它的 Makefile:5 硬编码了 KBUILD_CFLAGS += -Wimplicit-fallthrough=3，这是 GCC 专属写法；而 CachyOS 内核用 Clang 编译，未知警告选项在 -Werror 下直接失败。修法是 postPatch 把这个标志删掉 —— 它只控制警告等级，不影响代码生成。

顺带简化了旧 override：原来那段替换 installPhase 的代码是为 nixpkgs#575192 的 .ko.cer 聚合问题准备的。实测 CachyOS 的包集没有 aggregateModules（hasAggregate=false），而且默认 installPhase 自己就生成了 zenpower.ko.cer，所以那段可以删掉，只留 Makefile 补丁。

缓存必须一起改，否则前功尽弃：system/nix.nix 的 substituters 加了 https://cache.lantian.pub/lantian 和对应公钥。这是内核「零编译」的唯一原因 —— 不加就是几小时本地编译。

验证：

  • boot.kernelPackages.kernel.version = 7.3.1，name = linux-cachyos-latest-lto-zen4-7.3.1
  • hardware.nvidia.package = nvidia-x11-595.112.07，open = true，与原来版本一致（CachyOS 包集的 nvidiaPackages.stable 恰好也是 595.112.07）
  • boot.extraModulePackages = zenpower5 + nvidia-open-595.112.07-7.3.1（后者跟着内核重建）
  • 1847 条 assertion 全过，battery-saver specialisation 仍在
  • 整个 toplevel 构建成功
唯一不能零编译的部分：zenpower（约 10 秒）和 nvidia-open 内核模块（约 5 分钟，403 MiB）必须本地构建，因为它们要对新内核编译。内核本体是下载的。
安全网：A1 的 boot counting 已经开着。内核起不来会自动回退到上一代，不需要手动进 boot 菜单。
第一次重建有个先后顺序问题，我实测踩到了。把 substituter 写进 system/nix.nix 只改了下一次激活后的 /etc/nix/nix.conf；当前运行中的 nix-daemon 还不知道 lantian 缓存。于是第一次构建会把 LTO 内核本地重编 —— 我起了一次构建，8 分钟后发现它在跑 clang ... -flto=thin ... net/core/netpoll.c，正是本地编译内核。上游 README 也写了这一点："after adding binary cache to your NixOS configuration, please apply your settings once before enabling CachyOS kernel"。

两种顺序都对：
① 先只提交缓存那半（nix.nix 的 substituter + 公钥），nh os boot 一次让 daemon 认得缓存；再提交内核那半，第二次构建就走下载。
② 或者先用手动方式把内核灌进 store：sudo NIX_CONFIG="extra-substituters = https://cache.lantian.pub/lantian extra-trusted-public-keys = ..." nix build ...，然后再正常 nh os switch。
'
D2
全系统按 znver4 编译（gcc.arch / gcc.tune）
system/nix.nix 或新文件 风险 高 收益 高 等于全量重编译
▶

这是 AerynOS「官方仓库就是优化过的二进制」在 NixOS 上最直接的对位，但代价完全不同。

nixpkgs.hostPlatform = {
  system   = "x86_64-linux";
  gcc.arch = "znver4";   # 或保守用 "x86-64-v3" / "x86-64-v4"
  gcc.tune = "znver4";
};

我实测过这条能正常求值：gcc.arch 变成 znver4，并且 system-features 自动推导成 [… "gccarch-znver4" "gccarch-znver3" "gccarch-x86-64-v4" … "gccarch-x86-64"] 一长串 inferior 集合 —— 也就是说你的机器被声明为「能构建所有 znver4 及其下级的 derivations」。

nixpkgs 的 architectures.nix 里 znver4 的定义是 znver3 ∪ x86-64-v4，而 cc-wrapper 的 isGccArchSupported 表格里 znver4 需要 GCC ≥ 13（clang 需 ≥ 16），当前 nixpkgs 的 GCC 满足，所以 -march=znver4 会真的被传下去。

这是整个清单里代价最大的一项，请务必理解：
  • 换掉整个 stdenv 的 hash，cache.nixos.org 对几乎所有包失效。第一次等于全量源码编译：GCC、LLVM、Rust、Firefox/Chromium、整个 KDE/GNOME 栈。
  • 你机器是 16 核 Ryzen 7 8845H，22G 内存（已用 8.6G，14G available）。全量编译大概率要跑 十几小时到一天，且内存会成为瓶颈（max-jobs = 16 时并行编译 GCC/LLVM 容易 OOM）。
  • 编译产物只有你自己能用，社区缓存帮不上，每次 nix flake update 后新增的包还要再编。
  • 收益：AerynOS 宣称 x86-64-v3 相对 v1 有 5–20% 提升（这是 CachyOS 的数据）。但对日常桌面任务，感知通常远小于这个数字。
如果要做，正确的顺序是：
  1. 先做 D3（自建 attic 缓存），否则每次 rebuild 都是灾难。
  2. 先只对少数几个包用 .override 或 mkNixpkgs 局部优化，验证收益是否值得。
  3. 真要全量，把 max-jobs 降到 4–6、cores 设 0，并临时加大 swap/zram。
  4. 用 nixos-rebuild boot 而不是 switch，因为全量重编译期间系统还在跑老世代。
D3
自建 atticd 二进制缓存（D2 的前置条件）
system/attic.nix（新建） 风险 中 收益 中 长期基建
▶

只在你决定做 D2（或频繁自编内核包）时才有必要。nixpkgs 里有完整的 services.atticd 模块（我确认存在，默认 false），pkgs.attic-client 也有。

模块的默认值很省事：mode = "monolithic"、database.url = "sqlite:///var/lib/atticd/server.db?mode=rwc"、storage = { type = "local"; path = "/var/lib/atticd/storage"; }，且已经带了一整套 DynamicUser=true + PrivateTmp + MemoryDenyWriteExecute 的加固。

services.atticd = {
  enable = true;
  environmentFile = "/var/lib/atticd/env";   # 必填，模块里有 assertion
  settings = {
    listen = "127.0.0.1:8080";
    # 存储用默认的本地路径即可；要 S3 就覆盖整个 storage 块
  };
};

密钥按 assertion 提示生成：openssl genrsa -traditional 4096 | base64 -w0，写进那个 env 文件（ATTIC_SERVER_TOKEN_RS256_SECRET=…）。

几个现实问题：
  • 单机自建缓存在同一台机器上几乎没有收益（本机已经有的东西不需要缓存）。它真正有用的场景是「一台强机编译 + 推给笔记本」，需要两台机器。
  • /var/lib/atticd/storage 会吃掉大量空间。你 /nix/store 已经 65G，/ 剩 68G，全量 znver4 的缓存很可能撑爆。
  • 更轻的替代：services.nix-serve.enable（nixpkgs 自带，无去重、无多租户，但零配置），适合单机/局域网。
D4
把 auto-optimise-store 的「事后扫描」变成定期任务
system/nix.nix 风险 低 收益 低 你已开了一半
▶

已实施。system/nix.nix：

nix.optimise = {
  automatic = true;
  dates = [ "03:45" ];   # 默认值，写出来便于以后改
};

做了什么：auto-optimise-store 只对「从现在起写入的」内容做硬链接去重，已经躺在 store 里几个月的重复文件它不管。optimise.automatic 排一个全量扫过去。

验证（从产物读）：

  • nix-optimise.service 与 nix-optimise.timer 都已生成
  • timer：OnCalendar=03:45、Persistent=true、RandomizedDelaySec=1800（nixpkgs 自带的随机抖动，避免和其他机器同一秒开跑）
  • service 自带 ConditionACPower=true —— 用电池时不会跑，这条是 nixpkgs 给的，正好
  • service 里 CPUSchedulingPolicy=idle、IOSchedulingClass=idle、Nice=19，全量扫不会和你抢资源
和 AerynOS 的差距没变：Nix 的寻址单位是整个 derivation 输出（NAR），.stone 那种「包内自带去重 + 安装时按内容哈希落盘」的 CAS 做不到。这一项只是把已有能力用满，不改变模型。
想立刻跑一次：sudo systemctl start nix-optimise.service，或继续用 just gc。

E · 命令式体验 对应 AerynOS 的「像传统包管理器」

E1
comma：不用先查包名就能跑任意 nixpkgs 程序
system/comma.nix（新建） 风险 极低 收益 中 纯加包
▶

已实施，但修了上游的一个真实缺陷。

直接开 programs.comma.enable = true 是坏的。我实测：nixpkgs 的 comma 模块装出来的 fish/bash/zsh 钩子全都指向未包装的 comma 二进制，而它靠 ~/.cache/nix-index/ 下的数据库解析程序名。这台机器上那个目录根本不存在，于是每次补全都变成：
nix-locate failed with: ... I/O error: No such file or directory
连 comma -x hello 都跑不起来，不是「找不到包」，是直接报错。

修法：不动 comma 二进制，改为把预建数据库的路径导出成会话变量，让上游钩子原样工作。

# system/comma.nix（新建，已 import 进 system/init.nix）
# 数据库来自 nix-index-database flake；nix-locate 要的是一个名为 files 的目录
dbDir = pkgs.linkFarm "nix-index-database" { files = db; };

environment.sessionVariables.NIX_INDEX_DATABASE = "${dbDir}";
programs.comma.enable = true;

为什么要 linkFarm：flake 发布的 nix-index-small-database 是一个 1.7M 的文件，而 nix-locate 期待一个包含子项 files 的目录。直接把它当目录设进变量会失败。这一点是我实测出来的，不是文档写的。

验证（含反向对照）：

  • 构建产物 /etc/set-environment 里有 export NIX_INDEX_DATABASE="/nix/store/...-nix-index-database"，该目录下确有 files 软链
  • 在一个复刻真实 nixos-env-preinit.fish 路径的 fish 会话里跑不存在的命令，输出 No executable ... found in nix-index database —— 说明钩子真的读到了库
  • 去掉那个 export 再跑一次，报 database does not exist。反向对照失败，证明起作用的正是这个变量，不是别的东西碰巧生效
  • 真正存在的命令（如 rg）能正常解析出 ripgrep.out 并执行
附带收益：不需要跑 nix-index 建库（那要下载几百 MB 索引文件，耗时几十分钟）。数据库是随 flake 锁定的 1.7M 小库，随系统一起下载。
代价与限制：小库只含常用包的 /bin 索引，冷门包的程序名可能搜不到。environment.sessionVariables 靠 /etc/set-environment 下发，所以对 systemd 服务生效，但对不读该文件的场景（例如直接 env -i 起的进程）无效。
E2
让 rebuild 更快更安静（daemon CPU 策略 + 并行度）
system/nix.nix 风险 低 收益 中 纯调参
▶

已实施。system/nix.nix 三处改动：

# 1. 并行度：16 线程 / 22G 内存，别再让 16 个 job 各自跑满所有核
max-jobs = 8;
cores = 2;

# 2. daemon 自己降调度等级，编译不再抢你正在打字的会话
nix.daemonCPUSchedPolicy = "batch";
nix.daemonIOSchedClass = "best-effort";
nix.daemonIOSchedPriority = 6;

为什么是 8×2 而不是 16×0：原配置是 max-jobs=auto（解析成 16）配 cores=0（每个 job 用满所有核），等于最坏情况 16×16 线程抢 16 个核，再叠上 22G 内存里已用 9G 的现状 —— 大包必然 swap。8 个 job × 2 核 = 16，正好吃满而不超卖。

为什么 batch 而不是 idle：nixpkgs 文档明说 idle 可能「slow down and potentially starve crucial configuration updates」。rebuild 本身就是修系统的手段，把它饿死是自伤。文档给的判断标准正是「间歇性高负载的桌面/笔记本用 idle」，这里取折中的 batch。

验证（从产物读）：

  • $S/etc/nix/nix.conf 里确实是 max-jobs = 8、cores = 2
  • nix-daemon 的 drop-in 里有 CPUSchedulingPolicy=batch、IOSchedulingClass=best-effort、IOSchedulingPriority=6（注意：这些在 .d/overrides.conf 里，不在主 unit 文件里 —— 我第一次验证时看错文件，误判成没生效）
真话：这一项让编译「更安静」，不一定让单次 rebuild 更快 —— 并行度降了，总吞吐可能略低。换来的是编译期间机器可用，以及不会因为 OOM 整次构建失败重来。如果你更在意墙钟时间，把 max-jobs 调回 16、cores 保持 1。
E3
在文档里固化成「AerynOS 式」的日常流程
docs/ + justfile 风险 无 收益 中 纯文档
▶

已实施。两处改动，都不碰系统配置。

1. justfile 加四个目标（已 just --list 与 --dry-run 验证能解析、命令正确）：

just stage   # nh os boot .   建好并设为默认，但不激活；下次重启才变
just try     # nh os test .   立刻激活但不设为默认；重启自动退回
just undo    # nh os rollback 回到上一代并设为默认
just gens    # nixos-rebuild list-generations

2. docs/aerynos-workflow.md 记下两组对照：

  • 命令对照表：moss sync ↔ just switch、moss state list ↔ just gens、moss state activate N ↔ just undo、moss install foo ↔ nix shell nixpkgs#foo 或 , foo
  • 为什么 stage 与 try 值得分开放：AerynOS 换 /usr 是原子操作，天生没有中间态；NixOS 只能用「推迟到重启」来换取同样的「要么全变要么不变」。调桌面配置时用 try，别用 stage，因为 stage 写进 ESP 的世代会消耗 boot counting 的次数
零风险，且直接降低「在 NixOS 和 AerynOS 之间切换思维」的成本。这一项是清单里唯一不需要 rebuild 的。

F1
「内核级瞬时换根、进程不感知」—— 只能写进文档当结论
docs/ 风险 无 收益 低 认知对齐
▶

AerynOS 的做法是：新 /usr 在 /.moss/root 里建好，然后一个 renameat2(..., RENAME_EXCHANGE) 系统调用把它和活的 /usr 原地互换。NVMe 上 < 1 秒，已运行的进程完全不知道，下次 exec 自然用新文件。

NixOS 的 /run/current-system 是符号链接拓扑，不是一棵可交换的真实目录树，所以没有对应的原子操作原语。nixos-rebuild switch 只能逐个改 symlink + systemctl 重启单元，天然有中间态。

这一项没有任何 workaround。能选的只有：
  • 接受中间态：继续用 switch，快但有风险
  • 改为全量切换（A4 的 boot + soft-reboot）：原子但杀进程
  • 换系统：真的需要这个语义就去用 AerynOS / NixOS 之外的东西
这一项勾选 = 我把上面这段写进 docs/nixos-vs-aerynos.md，作为以后不再重复纠结的结论。
